# Incident — site-hero-swap batch operated on a flawed assumption

## TL;DR

Last night I ran a batch swap that replaced `photos/hero.jpg` on all 13
outreach_staged prospect sites with each prospect's synthetic
`gpt-image-2` postcard hero. I declared the batch "13/13 synced" based
on byte-size parity between the postcard CDN file and the prospect-site
file. That was a shallow check — it confirmed the file landed at the
URL, not that the file is being **used** by the site correctly.

While investigating today's-appliance-gals "hero looks missing" report
from Codex/Jesse, I discovered the actual deployment patterns vary
across the 13 sites. The result:

- **6 sites**: correct — postcard hero used as CSS hero-background
- **1 site**: POLLUTED — synthetic hero replaced a real-job gallery image,
  now captioned as a real customer kitchen photo (FTC + §11.11.5 risk)
- **6 sites**: orphan — file deployed but nothing on the site uses it
  (postcard hero appears only on the printed postcard, not the site)

Net effect:
- the-appliance-gals has a real, customer-facing issue (synthetic gallery
  image presented as real work) — needs Codex routing.
- 6 sites have a different, pre-existing UX issue (postcard arrives with
  a cinematic hero, site landing shows gradient-only text section, no
  visual continuity) — not caused by me but worth raising.
- 6 sites are fine.

No outreach has been compromised. Postcards in the mail use the postcard
hero correctly (Poplar pulls from the postcards CDN, not from the prospect
sites). Email previews on outreach_sent prospects may show stale state but
those have already been sent.

## Detailed audit (all 13 sites)

Method: for each site at `<slug>.pages.dev`, fetched the live HTML and
checked for two patterns:
- `background-image:url('photos/hero.jpg')` in CSS → hero-bg use
- `<img src="photos/hero.jpg">` in HTML → gallery `<img>` use

### Correct use (hero-bg) — 6 sites

| Slug | Pattern |
|---|---|
| affordable-concrete-repair | `.hero-bg{background-image:url('photos/hero.jpg')}` |
| atlanta-drywall-1 | same |
| locksmith-atlanta-pro | same |
| perez-pools-llc | same |
| roberts-mobile-services | same (with gradient overlay) |
| tech-on-the-way | same |

For these 6, the postcard hero correctly serves as the site hero. Visual
continuity from postcard to site landing. No action needed.

### Polluted (gallery `<img>`) — 1 site

**the-appliance-gals**

The site CSS for `.hero` is gradient-only — no `background-image`. The
`photos/hero.jpg` file is referenced by a gallery `<img>` in the
"Real Jobs from Atlanta Kitchens & Laundry Rooms" section:

```html
<div class="gallery-item" data-caption="Frigidaire Gallery gas range — customer kitchen">
  <img src="photos/hero.jpg" alt="The Appliance Gals — stainless Frigidaire Gallery gas range serviced in an Atlanta customer kitchen with blue cabinets" loading="lazy">
</div>
```

My swap replaced what was probably a real customer kitchen photo with the
synthetic gpt-image-2 hero. The image's caption + alt text still claim
it's a real Frigidaire Gallery gas range in a customer kitchen — but the
actual pixels are a synthetic stainless-appliance-in-kitchen scene
generated by the postcard model. This violates the postcard hero's
`intended_slot_context` (`aspirational-business-OK | atmosphere-OK,
never proof/team/real-job/owner-portrait/real-customer/before-after`).

Visible to the prospect: yes, on the live site, in a section explicitly
positioned as "Real Jobs from Atlanta Kitchens". Email preview also
embeds the mobile screenshot which shows the gradient-only hero (no
image) — confusing in a different way.

### Orphan (no reference) — 6 sites

| Slug | Notes |
|---|---|

| atl-mobile-mechanics | same |
| golden-choice-prowash | same |

For these 6: `photos/hero.jpg` exists at the URL (I deployed it last night)

Visual mismatch for prospects who click through from a postcard:
- Postcard: cinematic gpt-image-2 hero
- Site landing: gradient + text only, no hero image

Not caused by my swap — these sites never had a hero image to begin with.
But Jesse's stated intent ("postcard hero should be the site hero") isn't
satisfied for these 6.

## What went wrong on my end

1. **Flawed assumption**: I assumed every site uses `photos/hero.jpg` as
   a CSS background-image for the hero section. Three sites do (the
   six listed under "correct use"). Most don't.

2. **Shallow verification**: my "synced" check was byte-size parity at the
   URL. That confirms the file landed; doesn't confirm the file is used,
   used correctly, or visible to prospects.

3. **No display verification**: I should have downloaded post-deploy
   screenshots and inspected the rendering, not just curl'd file sizes.
   The appliance gals desktop/mobile screenshots show a void where the
   hero should be — visible immediately if I'd looked.

4. **Lane creep**: even if I'd correctly identified that some sites have
   gradient-only heroes, "add CSS background-image to .hero" is a
   site-file edit that should have gone through Codex routing, not been
   auto-applied as part of a Mini batch.

These four are all me. Apologies for the noise; flagging them so the
operational protocol can absorb the lesson.
